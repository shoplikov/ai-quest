    title: "Family only, or everyone?"
    why: "You feel the difference between 127.0.0.1 and 0.0.0.0 with your own hands."

      - "Find your machine's address on the network: `hostname -I` (take the first one, for example `192.168.1.20`)."
      - "Start the server for family only: `python3 -m http.server 8000 --bind 127.0.0.1`"

    title: "Name tags"
    why: "You see that a domain name is only a label for an IP address."

      - "Notice: the name chose the building. You still had to give the door number."

  - id: m4
    title: "Put a receptionist at the front door"
    why: "You set up a reverse proxy — the pattern almost every production service uses."
    steps:
      - "Install nginx: `sudo apt install nginx`. Check it answers: `curl -I http://localhost` (port 80 is the default for http)."
      - "Run your app for family only again: `python3 -m http.server 8000 --bind 127.0.0.1`"
      - |
        Create `/etc/nginx/sites-available/quest`:
        ```nginx
        server {
            listen 80;
            server_name quest.local;

            location / {
                proxy_pass http://127.0.0.1:8000;
                proxy_set_header Host $host;
                proxy_set_header X-Real-IP $remote_addr;
            }
        }
        ```
      - "Switch it on: `sudo ln -s /etc/nginx/sites-available/quest /etc/nginx/sites-enabled/`, then test and reload: `sudo nginx -t && sudo systemctl reload nginx`"
      - "Call it with no port number: `curl http://quest.local`"
      - "Stop the Python server and call again. Read the error. That is a `502 Bad Gateway`: the receptionist is there, the person behind door 8000 went home."
    check: "`curl http://quest.local` shows your file list, and you can produce a 502 on purpose and explain it."
  - id: m5
    title: "A secret tunnel"
    why: "You reach a service that is closed to the outside, the way engineers do every day."
    steps:
      - "You need any second Linux machine you can SSH into (a server at work, a small cloud instance, or a virtual machine). Ask your mentor for one if you have none."
      - "On that machine, start a family-only server: `python3 -m http.server 9000 --bind 127.0.0.1`"
      - "From your laptop, `curl http://<server address>:9000` fails. Good — it is private."
      - "Open a tunnel from your laptop: `ssh -N -L 9000:127.0.0.1:9000 <user>@<server address>`"
      - "In another terminal on your laptop: `curl http://localhost:9000`. You are now knocking on the server's private door from your own machine."
      - "Say the tunnel out loud: 'my port 9000 → through SSH → the server's 127.0.0.1:9000'."
    check: "The file list of the remote machine appears on `localhost:9000` on your laptop, and disappears when you close the tunnel."

You wrote an app. It runs. You send the link to a colleague and they say
"it doesn't open". Nothing is wrong with your code — the request never
found the right door. This level is about doors.

<Analogy />

## An address has two parts

Every network request needs two things: **which machine** and **which door
on that machine**.

```
http://192.168.1.20:8000/health
       └─ machine ─┘ └port┘
```

The machine part is an IP address (or a name that turns into one). The
port is a number from 1 to 65535. Some doors have traditional jobs: 22 is
SSH, 80 is http, 443 is https, 5432 is PostgreSQL. When a URL has no port,
the browser quietly uses 80 or 443.

<Diagram name="building-with-doors" />

## Listening: standing behind a door

When an app starts, it picks a door and waits. We say it **listens**. You
can see every listener on a machine with one command:

```bash
ss -tlnp
```

```
State   Local Address:Port   Process
LISTEN  127.0.0.1:8000       users:(("python3",pid=4242,fd=3))
LISTEN  0.0.0.0:22           users:(("sshd",pid=801,fd=3))
```

Read it as: "python3 stands behind door 8000; sshd stands behind door 22."
This command is your flashlight. When something is unreachable, look here
first — it replaces a lot of guessing.

## 127.0.0.1 and 0.0.0.0 — family only, or everyone

Look at the address column again. It answers a question people skip:
**who is allowed to knock?**

- `127.0.0.1` (also called `localhost`) means "only callers inside this
  same machine". It is the building's internal intercom.
- `0.0.0.0` means "every entrance of the building" — callers from the
  network can reach the door too.

<Diagram name="localhost-vs-all" />

So when an app works on the server but not from your laptop, the usual
reason is short: it listens on `127.0.0.1`. That is often a good default
— a database should not answer strangers. You open things to the outside
on purpose, never by accident.

## Refused or timed out? The two most useful errors

They sound alike. They mean opposite things.

| | Connection refused | Connection timed out |
|---|---|---|
| Speed | instant | slow — you wait |
| Meaning | you reached the machine; nobody is behind that door | no answer came back at all |
| Look at | is the app running? which address and port? | the IP, the firewall, is the machine up? |

Refused is rude but honest. A timeout is being ignored. Once you can tell
them apart, half of all "I can't connect" problems already point at their
cause.

## Names: DNS is a contact list

Nobody remembers `203.0.113.10`. DNS turns a name like `example.com` into
an address, the way your phone turns "Mum" into a number.

```bash
dig +short example.com
```

A name picks the building. It never picks the door — you still need the
port, unless it is the default 80 or 443.

## The receptionist: a reverse proxy

In production you rarely let people knock on your app's door directly.
You put **nginx** at the front door (80 and 443). It greets every visitor
and walks them to the right app inside — your app stays on `127.0.0.1`,
safe from the street.

<Diagram name="reverse-proxy" />

That is why one server can host many services under one address, and why
you will meet `502 Bad Gateway`: the receptionist is at the desk, but the
person she tried to call did not pick up.

## Tunnels: a private corridor

Sometimes a door is closed to the outside on purpose, and you still need
in — to look at a database, or to test an internal API. An SSH tunnel
gives you a private corridor:

```bash
ssh -N -L 5433:127.0.0.1:5432 user@server
```

Read it left to right: "door 5433 on **my** machine leads to
`127.0.0.1:5432` **as the server sees it**". Nothing is opened to the
world. Close the SSH session and the corridor is gone.

<Diagram name="ssh-tunnel" />

## What to remember

When something is unreachable, ask three questions, in this order:

1. **Is someone behind the door?** → `ss -tlnp` on the server.
2. **Who are they answering?** → `127.0.0.1` or `0.0.0.0`.
3. **Can the knock get there?** → right IP, right port, firewall, proxy.

Three questions. That is the whole level. The missions below make them a habit.
